## 1. 결론

**지금은 파일·버튼을 대량 삭제하기보다, 매도 경로·데이터 수집·상태 표시의 결함부터 해결해야 한다.** 기존 테스트 1,813개는 모두 통과했지만, 별도 적대적 검사에서 테스트가 잡지 못한 문제가 재현됐다.

최우선 네 항목은 다음과 같다.

1. 국내 prototype의 **2주 이상 매수 후 원매수 평균 체결가를 복원하지 못해 익절·손절이 차단되는 경로**.
2. **보유분 매도 점검이 관심종목 전체 조회 뒤로 밀리는 실행 순서**. 100종목의 요청 간격만으로도 분 단위 지연이 가능하다.
3. **실전 ON인데 연결 안내에는 ‘모의주문’이라고 표시되는 모순**. 실제 주문 차단 우회가 확인된 것은 아니다.
4. **수정주가 증분 수집에서 이전 가격 기준과 새 기준을 섞은 채 완료 처리할 수 있는 문제**.

총 **30개 검토 항목**을 정리했다. 이는 ‘확정된 버그 30개’가 아니라 **재현 결함, 정적 성능 위험, 유지보수 문제, UX 판단을 합친 목록**이다. P1 4개 / P2 18개 / P3 8개로 분류했다. 개선은 대부분 가능하지만, 국내 체결가 근거와 계정별 장부 이관은 외부 계약 확인 및 데이터 보존 절차가 필요하다.

이번 단계에서는 **감사 브랜치와 보고서·검증 산출물만 만들었다. 운영 코드·설정·DB·모델 수정, 파일 삭제·이동, 커밋·푸시, 계좌 조회·주문·자동매매 시작은 하지 않았다.**

## 2. 검증 범위와 한계

사용자의 ‘모든 코드·파일·기능’ 요청에 맞춰 **추적 파일 전체 인벤토리와 Python 전체 정적 목록화**를 수행했고, 실행·데이터·GUI 영역은 담당을 나눠 위험 중심으로 검토했다. 그러나 **모든 함수의 모든 입력 조합, 모든 브로커 응답, 모든 장중 경로를 검증한 것은 아니다.** 인벤토리 완성과 완전한 기능 검증을 같은 말로 사용하지 않는다.

| 항목 | 확인 결과 | 해석 |
|---|---:|---|
| 기준 Git 추적 파일 | 391개 | 전부 읽어 SHA-256 기록; 감사 전후 원본 바이트 변화 0개 |
| Python 파일 / 줄 | 260개 / 62,767줄 | 전부 AST 구문 분석; 실행 커버리지 수치가 아님 |
| 테스트 밖 Python | 131개 / 33,521줄 | 함수·메서드 정의 1,378개; 중첩 정의 포함 |
| 전체 함수·메서드 정의 | 3,856개 | 테스트 정의 포함; ‘기능 3,856개’라는 의미 아님 |
| 기본 데스크 GUI 목록 | 256항목 | 버튼 28개, 레이블 131개; Qt 내부 항목 56개 포함 |
| 기존 전체 회귀 테스트 | **1,813개 통과 / 518.610초** | 올바른 발견 명령 `unittest discover -s tests -v` 기준 |
| 구조화 파일 | JSON 44개, TOML/lock 2개, SVG 1개 파싱 성공 | 의미·금융 정확성까지 증명하지 않음 |
| 잠금 파일 | `uv lock --check` 통과 | 모든 연구용 별도 의존성까지 재현된다는 뜻은 아님 |
| 격리 wheel 빌드 | 성공 | 빌드 성공과 실행 성공이 다름: PKG-01 재현 |
| 장중·계좌·실제 체결 | 미실시 | 모의·실전 API 호출이나 주문을 하지 않음 |
| 성능 수치 | 합성 장부·오프라인 UI·가짜 시계 | 실제 장중 전체 지연/개선율/GPU 속도를 측정한 것이 아님 |

제외한 범위: 비밀값 내용, 운영 계좌/장부 내용 전수 조사, 모든 로컬 DB 행의 기업행사 대조, 새 학습·수익성 재검증, GPU 벤치마크, 가상환경 서드파티 전체 소스, 실제 고배율 Windows 화면·스크린리더 전수 시험. 개별 파일의 제한은 [파일 목록](files.md)에 표시했다.

자료 해석상의 오탐도 제외했다. Markdown 검사기가 `docs/mock-trading-hours.md`의 `RC4057` 오류 코드 예제를 링크로 오인한 한 건은 실제 깨진 링크로 세지 않았다. 분담 테스트 명령 두 건의 잘못된 모듈명도 도구 실행 실수이지 제품 결함이 아니며, 최종 결과는 별도 전체 1,813개 성공 실행을 기준으로 삼았다.

### 실행·GUI의 재현 요약

정확한 소스 위치와 각 승인 기준은 [실행 상세](execution.md), [GUI 상세](gui.md)에 있다.

- **RT-01:** 국내 파서 → 체결 복원 → lot 연결로 2주 보유가 확인되지만 `reconciled=false`, 익절·손절 가격은 모두 `None`. 기존 다주 테스트는 유효 `broker_average`를 직접 주입해 이 연결 결손을 놓친다. 마지막 단가나 계좌 합산 평균을 원매수 평균으로 둔갑시키는 방식은 금지한다. 임시로 미지원 매수를 제한할지는 별도 정책 결정이며 이번에 적용하지 않았다.
- **RT-02:** 가짜 100종목 조회의 호출 순서상 보유분 점검이 마지막이었다. DEMO 간격 1.25초 기준 99개 간격만 123.75초; 100조회에 각 1.25초를 부여한 가짜 시계는 125초다. **실제 장중 125초를 측정했다는 뜻은 아니다.** 우선순위 큐/작은 작업 단위와 최대 매도 점검 지연 기준이 필요하다.
- **RT-03:** 무관 이력 1천/5천/1만 행에서 empty 종목 inventory 조회 평균 9.18/42.89/86.19ms, pending 조회 8.97/42.32/85.43ms. 100종목×2모델의 두 조회를 단순 합하면 약 34초라는 **추정**이며 전체 순회 실측은 아니다. 실제 주문의 원자적 예약·마지막 검증은 유지한다.
- **RT-04:** 가짜 DEMO 키 A/B가 같은 임시 저장소에서 서로의 기록을 읽었다. 실제 사용자 계정 혼합 여부는 조사하지 않았다. 기존 장부를 새 키에 자동 귀속하면 안 된다.
- **RT-05:** timeout 10ms에 가짜 파이프 write 120ms를 넣었을 때 약 137ms 후 종료. 실제 무한 정지 실험은 하지 않았다. 시작·쓰기·응답 전체를 제한해야 한다.
- **RT-06:** 같은 시장·시각에서 두 bridge의 계좌 읽기 2회. 신호용 읽기만 공유하고 **주문 직전 fresh account 확인을 없애지 않는다.**
- **GUI-01/02:** 순수 상태 함수와 임시 JSON으로 재현. 실전 표기 모순 및 다중 source 진단 누락이지, 실전 주문을 시험한 결과가 아니다.

## 4. 데이터·연구 발견 사항과 승인 기준

### DATA-01 — 수정주가 증분 갱신의 가격 기준 혼합

근거: `dockdack/daily_dataset.py:393`, `463`, `512`의 기존 최신일·수정주가 요청·중단 조건과 `258`의 upsert. 기존 3일 종가가 100, 새 수정주가가 50이며 이전 날짜의 다음 페이지가 있어도, 겹치는 최신일에서 종료해 **100, 100, 50, 50**을 완료 상태로 남겼다. 실제 수집 함수를 가짜 응답으로 실행한 결과다.

이는 **현재 DB의 모든 급등락 원인이 이 코드라는 진단이 아니다.** 향후 수집/갱신의 무결성 결함이다. `history_cache.py`의 별도 수정 감지와 원본 전체 수집기의 동작도 다르다.

개선: 겹치는 구간의 수정 감지 → 종목별 임시 세대 재수집 → 검증 → 원자적 게시. 중단 시 이전 완성 세대를 보존하고, 원자료·기업행사 근거 없이 큰 변동을 임의 보정하지 않는다. 승인 기준은 분할/역분할 형태의 수정, 부분 실패, 재시작, 두 수집기 동시 접근에서도 한 종목의 게시된 이력이 동일 기준을 유지하는 것이다.

### DATA-02 / DATA-03 — 수집 응답 계약과 식별자 검증

근거: `dockdack/daily_dataset.py:495`의 `.get(response_key, [])`, `499`부터의 행 변환, `280`의 완료 기록 및 `389`의 완료 대상 건너뛰기.

- 정상 코드만 있고 필수 chart list가 없는 응답이 **0행·완료** 처리됐다. 필드가 명시적으로 존재하는 진짜 빈 목록과 필드 누락은 다르다.
- 요청 `005930`, 응답 종목 `999999`인 가짜 응답의 유효 일봉 1행이 **005930으로 저장**됐다.

개선: 페이지 전체 envelope, 필수 필드, 이용 가능한 응답 종목/시장, 날짜·수치 계약을 저장 전에 검증한다. 잘못된 페이지는 성공/완료가 아니라 재시도 가능한 오류로 남긴다. 승인 기준은 누락·잘못된 타입·다른 종목·부분 불량·정상 빈 목록·연속 페이지 중복의 구분이다. 실제 DB에 잘못된 종목이 들어갔다고 단정하거나 여기서 원본을 삭제하지 않는다.

### R-01 — DB의 물리 경로가 연구 정체성에 들어감

근거: `examples/train_mark1.py:60`, `examples/backtest_mark1_deep.py:107`, `examples/train_mark1_deep.py:314`, `examples/train_mark1_selective.py:315`, `examples/export_mark1_0504.py:82`. 동결된 `database_path` 및 일부 기본값이 옛 `dockdack-data-collection` 경로다. 새 단일 폴더의 정제 DB는 있지만 `load_frozen_cache`는 국내·미국 모두 옛 경로에서 `FileNotFoundError`가 났다.

개선: `dataset_id + content_sha256`를 불변 정체성으로, 실제 디스크 경로를 별도 설정으로 둔다. 과거 계약은 그대로 읽고 **해시로 검증한 경로 매핑**을 적용하는 새 호환 해석기를 만든다. 캐시 키를 전체 경로로 다시 만들거나 이전 manifest를 일괄 수정하지 않는다. 현재 안내의 오래된 경로도 별도로 갱신한다.

승인 기준: 다른 드라이브·공백/한글 경로·다른 컴퓨터 위치에서 같은 입력은 같은 실험으로 확인되고, 다른 바이트의 DB는 거부한다. 과거 계약에 봉인된 로더는 원본 보존 또는 버전 경계를 두고 변경한다.

### R-02 — 0.5/0.4 보고서의 절대경로 키 결합

근거: `examples/report_mark1_0504.py:102`. `artifact_sha256`의 키에 저장된 옛 절대경로와 현재 경로가 달라 국내·미국 모두 `Completed training/backtest provenance mismatch`. **옛 키의 digest와 현재 summary 바이트는 일치**했다. deep/selective 보고서 입력 읽기는 통과했으므로 전체 보고서가 다 망가졌다는 뜻은 아니다.

개선: artifact 논리 ID로 확인하되 과거 절대경로 키의 명시적 호환 매핑을 허용한다. 파일명만 같은 임의 파일을 허용하거나 해시 검사를 제거하지 않는다. 승인 기준은 이동 전후 동일 보고서 입력 검증 성공과 변조 입력 실패다.

### R-03 — Windows 줄바꿈으로 동결 소스 해시 불일치

근거: `.gitattributes`에서 `dockdack/mark1_deep_models.py` 보호가 빠져 있다. 실제 deep 동결 검사에서 국내·미국 모두 `Frozen training code changed`가 났다.

현재 파일은 15,652바이트 CRLF이고 SHA-256은 `d6ac2b375ae5c8078ce5770e5ff24550a2715e0b9e0b1eb067ed7cc4e07d847d`. **메모리에서만 LF로 변환**한 15,350바이트는 저장된 기대 해시 `50ae22f70278a9cd4ca0fb276d20260a2421c9874ac8f35846a10529d15d16d7`와 정확히 같았다. 파일은 수정하지 않았다.

deep 6/7개, selective 10/10개, half 13/13개의 코드 해시가 일치했다. 앞선 정리에서 일부 모델의 봉인을 보존했다는 사실이 모든 과거 연구 소스의 봉인까지 보장하지는 않는다.

개선: 알려진 원본 바이트 복원, 전체 frozen 목록 기반 Git 속성·검사 자동화. 잘못된 현재 바이트로 기대 해시를 새로 봉인하지 않는다. 승인 기준은 깨끗한 Windows checkout에서도 **모든** 보존 계약이 성공하는 것이다.

### R-04 — 연구 데이터 메모리·I/O 비용

근거: `dockdack/mark1_data.py:210`, `243`, `258`, `294`; `examples/train_mark1.py:65`, `73`, `81`; `examples/train_mark1_selective.py:80`, `125`; `examples/train_mark1_0504.py:105`, `175`; `dockdack/mark1_selective_models.py:273`.

학습 샘플 인덱스를 제한해도 전체 bar bank가 남고, NPZ 배열이 메모리로 풀리며, 큰 float32 특징 행렬을 전체 생성한 다음 저장해 다시 mmap으로 연다. cache hit에서도 DB 전체 해시를 앞뒤로 읽고, 같은 배열의 해시를 모델/seed별 반복 계산하는 경로가 있다.

메타데이터 확인값: 원시 cache NPZ 2개 774,315,016바이트; selective 특징 20파일 6,534,365,856바이트; half 특징 20파일 6,532,818,048바이트. 최대 특징 파일 1,104,000,128바이트. **파일 용량은 peak RAM도 속도 측정값도 아니다.**

개선: 새 버전에서 chunk 단위 특징 생성, `open_memmap`에 바로 기록, 동일 불변 산출물의 해시/공유 bank 재사용, 완성 manifest를 원자 게시. 무결성을 위해 필요한 검사를 무조건 없애지 않는다. 승인 기준은 기존 특징·예측 수치 동등성, 실패 후 불완전 cache 거부, 실제 RSS/CPU/I/O 및 cold/warm 실행 시간 비교다. 속도 향상 비율은 아직 제시할 수 없다.

### R-05 — 연구 환경 의존성의 비표준 위치와 불완전한 안내

근거: `examples/train_mark1_selective.py:322`는 LightGBM을 가져오지만 `pyproject.toml`의 `ml`/`prototype` extra는 LightGBM을 포함하지 않는다. 별도 `requirements-selective.txt`는 존재하며 현재 로컬은 `outputs/mark1/selective-deps`로 보완돼 있다. 그 파일 1행은 존재하지 않는 `requirements-ml.txt`를 안내한다.

‘의존성이 아예 없다’가 아니라 **표준 설치와 실제 연구 환경 구성이 분리된 문제**다. outputs를 임시 파일로 보고 지우면 실행도 깨질 수 있다.

개선: GUI/브로커 최소 환경과 연구/CUDA 환경을 명시적으로 분리하고 각 설치 조합·lock·진입점을 문서화한다. 승인 기준은 새 격리 환경에서 기존 outputs 의존성 없이 선택 모델 학습 import·작은 smoke·prototype worker가 성공하는 것이다. 대형 재학습은 별도 단계다.

### R-06 — 중복 제거와 연구 봉인의 충돌

전체 AST에서 유사 함수 본문 묶음 12개를 찾았으나, 여러 항목은 `mark1_backtest`와 `mark1_0504_backtest`, 버전별 inference의 의도적인 과거 계약이다. **중복이라는 이유만으로 제거하면 과거 실험 근거가 바뀐다.**

개선: 역사적 v1 코드·해시를 보존한 채 다음 버전의 공통 데이터/장벽/비용/보고 코어를 설계한다. 시장·장벽 정책은 명시적 설정 객체로 분리하되 골든 입력으로 예측/거래/비용/양쪽 장벽 시 손절 우선 결과가 동등한지 검증한다. 승인 기준은 과거 재현 성공과 새 버전 비교 보고서이며 파일 수 감소 자체가 목표가 아니다.

### 모델 의미와 백테스트 한계 — 새 결함으로 중복 집계하지 않음

현재 선택된 CatBoost prototype 학습은 **실제 당일 시가 진입 샘플**을 사용한다. 초기 sequence/deep 연구의 가상 매수가 증강과 다르다. 추론 때 현재 가격을 넣을 수 있다는 사실이 **장중 그 시점 이후 +목표/-손절 도달 순서의 성공확률을 검증했다는 뜻은 아니다.** 일봉만으로 장중 경로 순서를 관측할 수 없으며 양쪽 도달은 손절 우선이라는 보수적 규약이다.

추가로 이미 알려진 한계인 재사용 평가 기간, 당시 투자 가능 종목 집합/생존편향, 일부 기업행사, 정제된 학습용 bar와 완전한 체결 평가용 패널의 차이, 고정 비용 가정은 최적화로 사라지지 않는다. `mark1_prototype`, `mark1_0504`, `mark1_1_prototype`의 portable manifest 검사는 통과했으며 연구용·장중 검증 미통과·배포 부적격 경고는 유지돼 있다. **파일 무결성과 모델의 수익성은 별개다.**

## 5. 배포·테스트·구조 문제

### PKG-01 — 저장소에서는 되지만 일반 설치 배포는 닫혀 있지 않음

근거: `pyproject.toml:43` 이후 패키지 탐색은 `dockdack*`만 포함하고 자산은 SVG/ICO다. `dockdack/prototype_external.py:205`는 `-m examples.run_prototype_signal`을 실행하며, 같은 파일의 `ROOT`와 모델 경로는 저장소 위치를 전제로 한다.

실제 `git archive HEAD`를 임시 폴더에 풀어 **의존성 다운로드 없이 wheel 빌드**했다. 빌드는 성공했지만 93개 wheel 구성원에 `examples`와 `models`는 없었다. 저장소 밖에서 wheel만 `PYTHONPATH`에 두고 `python -S -m examples.run_prototype_signal --help`를 실행하면 `ModuleNotFoundError: No module named 'examples'`가 난다. 이 검사는 기존 환경에 패키지를 설치하거나 실제 worker를 주문에 연결하지 않았다.

개선: 운영 worker를 설치 패키지의 정식 진입점으로 옮기고, 모델은 버전·해시가 있는 배포 묶음/설정 경로로 명시한다. 모델을 무조건 wheel에 넣으라는 뜻은 아니다. 승인 기준은 저장소 바깥의 새 환경에서 일반 GUI·worker·모델 로딩 smoke가 성공하며, 모델 누락은 사용자에게 명확한 오류로 표시되는 것이다.

### QA-01 — 개발자 검증 명령을 프로젝트가 보장하지 않음

`python -m unittest discover -q`는 **0개 테스트, `NO TESTS RAN`, exit 5**였다. ‘성공으로 위장한 green’이 아니라 명시적 실패다. 반면 `-s tests`를 지정하면 1,813개가 통과했다. README의 개발 테스트 명령, 루트 검증 task, tracked CI 구성, lint/coverage 표준은 확인되지 않았다.

개선: 단일 개발 검증 진입점에 명시적 `unittest discover -s tests`, 필요한 Qt offscreen 환경, 형식/봉인/패키지 smoke를 묶는다. 새 결함별 통합/성능 회귀를 추가한다. unittest를 전부 pytest로 바꾸는 것이 선행 조건은 아니다. 이번에는 branch/line coverage 도구를 실행하지 않아 커버리지 백분율을 제시하지 않는다.

### ARCH-01 — 역할 경계가 큰 파일과 버전 상속에 묻혀 있음

대표 파일은 `watch_gui.py` 1,920줄/함수 89개, `kiwoom.py` 1,617줄/76개, `watchlist.py` 1,112줄/63개, `autotrade.py` 1,051줄/41개다. `watch_gui._build`는 272줄이고 backtest `simulate_portfolio`는 293~302줄이다.

이 숫자는 **읽기·변경 범위가 크다는 지표이지 느리다는 측정 증거가 아니다.** 먼저 실제 병목을 고친 다음 화면 구성/상태/작업자, 계좌/주문/시세 파서, 장부/관심종목/신호 저장소를 나눈다. 기존 import·CLI·봉인 계약을 동시에 부수는 전면 이동은 피한다.

## 6. 무엇을 유지하고, 숨기고, 합치고, 지울 수 있는가

‘최적화되지 않았다’는 이유만으로 기능을 삭제하지 않는다. 기능 가치, 현재 참조, 데이터 복구 가능성, 실제 비용을 각각 판단한다.

| 대상 | 권장 판단 | 조건/이유 |
|---|---|---|
| 자동주문 ON / OFF / 감시 시작 / 감시·주문 중지 | **유지** | 주문 권한과 조회 상태는 서로 다름; 접수 주문 취소와도 다름 |
| 두 prototype 독립 체크 및 동일 종목의 모델별 lot | **유지** | 서로 다른 모델의 매수 허용·원매수별 매도 요구사항 |
| 동일 신호 재전송 방지·미확정 주문 대조·잔고/매도 수량 검증 | **유지** | 다른 모델 중복 매수와 전송 중복 방지는 별개 |
| 실전/모의 배지·원가 미확인·접수≠체결·수수료/모델 미검증 안내 | **유지/명확화** | 불필요한 문구가 아니라 해석·위험 경계 |
| 기본 연결/설정 연결의 중복 탭·상단 바로가기 | **통합 후보** | 소스별 상태·설정·검사를 하나의 정보 구조로 |
| 긴 절대경로·반복 버전/도움말 | **접기/상세보기 후보** | 핵심 상태를 가리지 않게 축약; 복사/진단 기능 유지 |
| 파일 검사 / 신호 1회 읽기 | **구분 유지** | 전자는 검사, 후자는 후보 접수라는 효과 차이 명시 |
| 랜덤 모의 신호기·내장 LSTM·임의 JSON source | **고급/레거시로 분리** | 일반 사용자 흐름에서 감추되 현재 의존성 확인 후 삭제 판단 |
| 숨겨진 builtin_lstm 체크 등 호환 연결용 위젯 | **조건부 삭제 후보** | 콜백/상속/테스트가 상태 객체로 대체된 뒤 삭제 |
| 과거 전용 mark1 GUI | **연구/관찰 도구로 분리** | 관찰 전용 주문 차단은 독립 역할; 단순 중복 아님 |
| preview 스크립트·재생성 캐시/pyc | **조건부 정리 후보** | 실행 진입점·테스트·복구/재학습 의존성 확인 후 |
| 원본/정제 DB, 장부, 복구 bundle, 모델/manifest, 과거 보고서 | **보존** | 재현·회계·원매수 추적·복구 근거 |
| 약 13GB 특징 cache, 연구 checkpoint | **즉시 삭제 보류** | 재생성 시간·재시작 필요성·입력 존재 확인 후 archive/정리 선택 |
| `outputs/mark1/*-deps` | **즉시 삭제 금지** | 현재 실제 실행 환경 일부; 환경 이전 검증이 먼저 |
| 불명확한 수동 거래/원가 | **삭제/임의 배분 금지** | 증거 기반 대조 UX와 이관 절차를 마련 |

‘삭제가 확정된 운영 기능’은 이번 감사에서 지정하지 않았다. 경로/의존성/회귀를 통과한 후 삭제할 **후보**와 반드시 보존할 것을 구분했다. 버튼·텍스트 각각의 판정은 [256항목 표](controls.md)에 있다.

## 7. 권장 프로젝트 구조

현재 flat layout도 유효한 Python 구조다. ‘대부분 이렇게 쓴다’는 단정 대신, 이 프로젝트에서 드러난 **저장소 밖 실행 실패·운영/연구 혼재·경로 고정**을 줄이는 방안으로 설치 중심 `src` 구조를 권한다. PyPA는 src layout이 저장소 루트의 우연한 import를 줄여 설치물 문제를 드러낸다고 설명한다. 다만 개발용 editable 설치가 필요해진다. [PyPA 설명](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)

다음은 **최종 목표안이지 이번에 옮긴 폴더가 아니다.** 세부 모듈 이름은 실제 의존성 경계를 확인하며 조정한다.

```text
dockdack/
├── pyproject.toml / uv.lock / README.md / DEVLOG.md
├── DockDack.vbs                     # Windows 사용자 진입점 유지
├── src/dockdack/
│   ├── app.py                      # 구성·환경·서비스 조립
│   ├── cli/                        # GUI/수집/worker 정식 진입점
│   ├── broker/kiwoom/               # 시세·계좌·주문·응답 파서
│   ├── trading/                     # 실행·리스크·체결 복원·lot
│   ├── signals/                     # 외부 프로토콜·worker·모델 adapter
│   ├── persistence/                 # DB schema·migration·저장소
│   ├── data/                        # 수집·정제·식별·이력 cache
│   ├── ui/                          # views / models / workers / assets
│   └── core/                        # 시간·설정·공통 값 객체; 잡동사니 금지
├── tests/
│   ├── unit/ / integration/ / contracts/ / performance/
│   └── fixtures/                    # 가짜 broker·작은 DB·golden 입력
├── research/
│   ├── experiments/                 # 다음 버전 학습/백테스트
│   └── legacy/                      # 보존 계약을 지킨 과거 연구
├── examples/                        # 짧은 API 사용 예제만
├── scripts/                         # 개발/패키징 보조 도구
├── docs/user/ / developer/ / research/ / audits/
├── models/                          # 버전·해시·배포 경로가 명시된 모델
├── reports/                         # 과거 실험·평가 보고서 보존
├── data/                            # ignored; raw / clean / manifests
├── outputs/                         # ignored; 새 실험·cache·감사 증거
└── .dockdack/                       # ignored; 계정별 운영 상태·복구
```

### 현재 → 목표 매핑과 위험

| 현재 | 목표/역할 | 이전 전에 반드시 확인할 것 |
|---|---|---|
| `watch_gui`, `v00_app`, 각 `*_gui` | `ui` 화면/상태/작업자 + app 조립 | 기존 launcher/import·중지 동작·모드 표시 회귀 |
| `kiwoom.py`, `http.py` | `broker/kiwoom` 파서와 전송 | API façade 유지, 주문 직전 guard 보존 |
| `autotrade`, `execution_policy`, `strategy_lots`, `fill_recovery` | `trading` | 원매수·부분 체결·정정·취소·재시작 계약 |
| `watchlist.py` | `persistence` 저장소와 migration | schema/ID/기존 장부 보존, transactional claim |
| `prototype_external`, `signal_bridge`, 운영용 examples | `signals` + 정식 worker CLI | 표준 설치 smoke, 다중 모델·동일 종목·재전송 경계 |
| `daily_dataset`, `history*`, `dataset_*` | `data` | 수정주가 세대·원본보존·논리 ID |
| `mark1_*` 연구 소스 + train/backtest/report 예제 | `research`의 새 버전; 기존 버전은 보존 | **봉인 파일은 import 이동 자체도 계약 변경**; 호환 스냅샷/로더 필요 |
| `models`, 정제 DB, `outputs` | artifact registry가 경로 해석 | 내용 해시 기반 경로 이동, 과거 manifest 불변 |
| 임의 `outputs/*-deps`, 여러 requirements | 명시된 GUI/연구 환경 | 새 환경 검증 전 이전 환경 삭제 금지 |
| docs·README·DEVLOG | 사용자/개발자/연구 기록 분리 | 링크와 명령 갱신; 당시 기록은 유지 |

폴더만 나누는 것으로 최적화가 되지는 않는다. 공개 import 호환 shim과 작은 단계별 이관을 사용하고, 동결 소스는 우선 제자리에 보존해도 된다. 보존 영역까지 억지로 새 모양에 맞추는 것이 목표는 아니다. pytest의 권장 개발 관행도 설치된 패키지와 테스트 경계를 분리하지만, 기존 unittest 테스트 자산을 버릴 이유는 없다. [pytest 공식 문서](https://pytest.org/en/stable/explanation/goodpractices.html)

## 8. 후속 구현 순서와 완료 기준

| 순서 | 작업 | 완료로 인정할 증거 |
|---:|---|---|
| 1 | 정확성: 국내 체결가, 수집 검증/수정주가, 실전 문구 | 실패를 재현하던 테스트가 먼저 추가되고 정상/악성 입력 모두 통과 |
| 2 | 매도 응답성·RPC 전체 deadline·계정 scope | 100/500종목·느린 모델·DB 잠금·계정 변경·재시작에서 명시한 불변 조건 유지 |
| 3 | 연구 경로/줄바꿈/환경 재현 | 옛 계약 불변, 새 위치에서 report/검증 성공, 변조 입력 거부 |
| 4 | 계측된 병목: SQL, 계좌 snapshot, UI worker/delta, 연구 chunk | 같은 출력/장부를 유지하며 before/after 시간·I/O·RSS 측정 |
| 5 | 연결 화면 통합·짧은 문구·접근성·노트북 레이아웃 | 주요 기능 접근성, 화면별 동작 차이, DPI/키보드 검증 |
| 6 | 설치 계약과 src/도메인 구조 이전 | 저장소 밖 wheel smoke, 전체 회귀·봉인 검증, 옛 진입점 호환 |
| 7 | 참조 끊긴 코드/캐시 정리 | 소비자 없음·재생성/복구 가능성 증거·정확한 삭제 목록 |

GUI의 긴 계산을 작업자로 옮기되 QWidget 조작은 GUI 스레드에 남겨야 한다. 단순히 모든 코드를 스레드로 옮기거나 주문 전송자를 여러 개 만드는 것은 안전한 최적화가 아니다. [Qt 스레드/객체 공식 문서](https://doc.qt.io/qt-6/threads-qobject.html)

전체 공통 승인 기준: 모델별 같은 종목 매수 허용, 원매수별 매도 배분 유지, 미확정 주문 재전송 금지, 보유량 초과 매도 금지, 계정 간 장부 분리, 과거 연구 재현 보존, 주문 OFF/실전 확인 의미 불변. 개선을 이유로 이 조건을 제거하지 않는다.
