## RT-01 — 국내 다주 매수 후 모델별 청산이 막히는 연결 결손

## RT-02 — 매도 점검이 100종목 매수용 순회 뒤에 대기

- 근거: `dockdack/autotrade.py:940-1032`에서 관심종목 루프가 끝난 뒤에만 `_holdings_pass`를 호출한다. 정규 보유분 매도 신호는 외부 모델에서 생성하지 않고 GUI 보유분 순회에 위임한다(`mark1_trigger.py:86-93`).
- 재현: 100개 임시 관심종목에 대해 가짜 `snapshot` 호출 순서를 기록하면 100번째 조회 이후에 처음 보유분 순회가 호출된다. 실제 주문 수는 0.
- 시간 모형: 기본 DEMO 조회 간격은 1.25초(`http.py:51,207`). 100회 시세 요청 사이 간격만 약 123.75초이며, 각 조회에 1.25초를 부여한 가짜 시계 모형은 125초였다. 첫 요청의 즉시 전송 여부에 따른 차이가 있으므로 '정확히 125초 보장 지연'이 아니라 **대략 2분 규모의 구조적 지연**이다. 일봉/계좌/추론/재시도 지연을 넣으면 늘 수 있다. 실측 장중 지연은 측정하지 않았다.
- 영향: 0.4% 손절처럼 작은 장벽의 감시 주기는 UI 타이머 수치와 다르며, 중간 가격 도달을 놓칠 수 있다. 느린 관심종목 하나도 보유분 매도 점검을 밀어낸다.
- 개선: 읽기 작업을 작은 단위의 우선순위 큐로 바꾸고, 보유분 가격/미체결 점검에 최대 대기시간 예산을 준다. 신규 매수 탐색 사이에 보유분 점검을 끼우며, 하나의 주문 실행자·HTTP 제한·마지막 전송 검증은 유지한다. 가능하다면 검증된 실시간 가격 경로를 별도 검토한다.
- 승인 기준: 100/500 관심종목, 느린 데이터 응답, 모델 한 개 정지 상태에서 보유분 최초/최대 재점검 지연을 가짜 시계로 제한하는 테스트.
- 개선 가능성 높음 / 비용 대 / 신뢰도 높음 / 단순히 매도 검증 삭제·주문 스레드 무제한 추가하는 변경은 위험 매우 높음.

## RT-03 — 종목별 장부 조회의 전체 이력 스캔

- 근거: `watchlist.py:555-562`가 `_order_history(db, None)` 및 모든 배분을 먼저 가져온 뒤 Python에서 `watch_id`로 거른다. `prototype_pending_buys`도 전체 `order_history(None)`을 다시 읽는다(`577-586`). `prototype_sell_allocation`도 모든 배분을 순회한다(`594-599`).

- 측정: 서로 무관한 종목의 주문 1천/5천/1만 건을 만든 후, **이력이 없는 종목**을 조회했다. 각각 5회 평균.

| 전체 장부 행 수 | inventory 평균 | pending 평균 |
| --- | ---: | ---: |
| 1,000 | 9.18 ms | 8.97 ms |
| 5,000 | 42.89 ms | 42.32 ms |
| 10,000 | 86.19 ms | 85.43 ms |

- 해석: 결과가 0건이어도 누적 이력 크기에 비례한다. 100종목×2모델이 두 조회를 한 번씩 하는 단순 합산은 약 34초다. 이는 실측 전체 순회 시간이 아니라 위 비용의 선형 추정이고, 기타 비용을 제외했다.
- 개선: `_order_history`와 배분 조회에 SQL `WHERE watch_id=?`, 상태 필터 및 인덱스를 추가한다. 신호/화면 읽기에는 한 DB 스냅샷 또는 `ledger_revision`별 종목 투영 캐시를 공유한다. 실제 주문의 원자적 claim/예약 및 마지막 확인에서는 변경 버전을 재검증한다.
- 승인 기준: 무관 이력 1만/10만 건 증가 시 특정 종목 empty lookup 비용이 거의 일정; 같은 종목의 전체 관련 이력과 재시도·수동 매도는 누락 없이 유지.
- 개선 가능성 높음 / 비용 중 / 신뢰도 높음 / 데이터를 삭제해 빠르게 만드는 우회는 불가.

- 근거: `gui_service.py:55-73`은 REAL만 키 스냅샷 및 해시 범위를 만들고 DEMO는 항상 `demo`. `environment_store.py:47-56`, `watchlist.py:1104-1112`는 DEMO를 동일 `watchlist.sqlite3`로 연다. `autotrade.py:323-335`, `fill_recovery.py:113-118`의 키 범위 대조도 REAL에만 적용한다.
- 재현: 서로 다른 가짜 DEMO AppKey A/B 서비스를 만들고 같은 임시 base 폴더를 전달했다. 두 서비스 scope가 모두 `demo`, DB 경로가 같고 B가 A의 기록을 읽었다. HTTP 호출 0.

- 개선 가능성 높음 / 비용 중 / 신뢰도 높음 / 기존 장부 경로를 무작정 이동·덮어쓰기할 위험 높음.

## RT-05 — RPC 제한시간은 전체 요청 마감시간이 아님

- 근거: `prototype_external.py:236-248`에서 프로세스 시작 후 `stdin.write`/`flush`를 동기 실행하고, 그 뒤의 응답 Queue에만 timeout을 준다. `close`도 같은 RLock을 잡는다(`266-283`).
- 재현: HTTP/실제 자식 없이 가짜 stdin.write를 0.12초 지연시키고 timeout=0.01초로 요청했다. 실제 종료는 약 0.137초였다. 설정 제한시간 밖에서 입력 쓰기를 기다린다는 것을 확인했다. 실제 파이프 무한 정지는 강제로 발생시키지 않았다.
- 영향: 모델 시작/import 정지, 자식이 입력을 읽지 않는 상태, 큰 메시지로 파이프가 차는 경우 제한시간이 보호하지 못한다. 동일 worker에 달린 감시/종료가 계속 대기할 가능성이 있다. 주문 전송 자체가 발생했다고 주장하는 것은 아니다.
- 개선: 프로세스 시작·쓰기·응답을 합친 단일 monotonic deadline, 제한된 송신 큐/쓰기 작업자, 취소 가능한 통신, 종료 시 writer 해제를 도입한다. 성공 응답 식별자 검사와 실패 시 HOLD는 유지한다.
- 개선 가능성 높음 / 비용 중 / 신뢰도 높음(타임아웃 경계); 무한 정지는 미검증 / 보호 코드 삭제 위험 높음.

- 영향: 정상 동시 모델 연결만으로 신호 생성을 위한 계좌 읽기가 중복된다. 실제 `account_domestic`/`account_us`는 각 잔고+예수금 요청이므로 API 제한 대기 및 RT-02 지연이 늘어난다(`kiwoom.py:427-525`).
- 개선: 주문 실행자 바깥이 아니라 **부모 GUI worker**에 환경/키 범위·시장별 읽기 스냅샷 제공자를 두어 두 모델에 같은 조회시점 데이터를 전달한다. 모델별 가상 보유 투영은 각자 유지한다. 주문 직전 fresh account 및 실행 검증은 캐시로 치환하지 않는다.
- 개선 가능성 높음 / 비용 소~중 / 신뢰도 높음 / 중복 조회 제거는 적절, 주문 직전 재검증 제거는 부적절.

## RT-07 — 비주문 상세 이력의 수명 정책 없음

- 근거: `signal_bridge.py:309-319`에서 매 export를 DB에 추가하고, `440-452`에서 HOLD를 포함한 각 신호·수신 이벤트를 저장한다. `autotrade.py:432-435`는 각 조회마다 monitor 이벤트를 저장한다. `watchlist.py:713-722`는 만료 상태만 변경하며 관련 행을 지우지 않는다. 소스에서 이 테이블을 아카이브/보존기간 처리하는 경로를 찾지 못했다.
- 영향: 장기간 실행 시 SQLite/백업 크기와 시작/조회 비용이 계속 증가한다. 모델 결정 추적 및 재전송 방지에 필요한 정보도 있어 모두 '쓰레기'로 취급하면 안 된다. 현재 실사용 DB의 크기/증가율은 읽지 않았으므로 실제 용량 문제라고 단정하지 않는다.
- 개선: 주문·체결·원매수 provenance·재전송 tombstone은 영구 보존하고, 고빈도 monitor 원문/참조되지 않는 오래된 chart 상세/HOLD 상세는 압축 아카이브·집계로 분리한다. 키 무결성·재시작 replay 차단이 보존되는지 먼저 정의한다. 필요하면 WAL/배치 쓰기를 별도 벤치마크하되 DB 모드 변경을 성급히 적용하지 않는다.
- 개선 가능성 높음 / 비용 중 / 신뢰도 중상(정적 경로 확인) / 무분별한 삭제 위험 매우 높음.

## 제거 대상으로 판단하지 않은 것

- 다른 모델의 같은 종목 매수는 요구사항이며, 각 모델 원매수별 매도 배분을 유지해야 한다. 같은 신호 재전송 방지·출처 불명 pending 차단은 별개다.
- 계좌 전체 잔고와 모델별 장부 불일치 시 임의로 평균/소유를 추정하지 않는 것은 올바르다. 방어 제거가 아니라 정상 경로와 복구 절차를 완성해야 한다.
- 브로커 주문 접수와 실제 체결의 구분, 미확정 결과 자동 재주문 금지, REAL 수동 확인, 모델 출처 확인, 원자적 SQLite claim 및 마지막 HTTP send guard는 삭제 불가.
- 현재가 지정가 주문은 손절 장벽의 정확한 가격/체결을 보장하지 않는다. 이 한계를 숨기는 문구 삭제 대신, 사용자 정책 선택과 명시가 필요하다.
- 전체 장부 기반 모델별/FIFO 손익 계산은 주문 페이지 몇백 행만으로 대체하면 안 된다.
- `_messages`에는 4096/512 정리, 모델 진단에는 500개 한도가 이미 있다. 이 부분을 무제한 메모리 누수라고 지적하지 않는다.
- 신호 시각은 `signal_bridge.timestamp`에서 UTC로 정규화하므로 ISO 시간대 문자열 정렬 문제를 이 경로의 결함으로 지적하지 않는다.
