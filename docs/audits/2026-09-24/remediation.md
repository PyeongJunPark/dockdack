## 가장 중요한 동작 변경

- 보유분 매도를 신규 관심종목 조회보다 먼저 점검한다. 이후 조회 10건 또는 30초가 지나면 다시 보유분을 확인한다. 같은 작업자가 순차 처리하므로 진행 중 API/모델 호출을 중간에 끊는 하드 실시간 보장은 아니다.
- 일반 GUI에 **모의계좌 정규장 마감 5분 전 전체 보유 청산**을 기본 선택으로 연결했다. 앱 실행, 감시, 사용자의 자동주문 ON 승인이 모두 필요하다. 이 개발 작업에서 자동주문을 켜지 않았다.
- 조회 대기시간이 길어도 5초 idle 점검이 같은 주문 작업자를 깨운다. 정상 조회의 예약 시각을 뒤로 미루지 않으며, 이미 작업 중이면 해당 작업의 checkpoint에서 확인한다. 계정 전환 시에도 대상 장부 잠금을 먼저 확보한다.
- 대상은 모델이 산 종목뿐 아니라 **모의계좌의 모든 국내·미국 매도가능 보유**다. 휴장·서머타임·조기 폐장 일정을 사용하고 마감 구간의 새 매수는 차단한다. 마감 청산에만 평소 수량/금액 한도 예외를 적용한다. 실전 전량매도는 켜지지 않는다.
- 지정가 주문이 접수되어도 체결/전량 소진은 보장하지 않는다. 미확정·미체결 주문, 수량 불일치, 미지원 거래소 등은 중복 전송하지 않고 미청산 사유로 남긴다. 앱 종료·컴퓨터 절전·통신 장애 때 대신 거래해 주는 서버는 없다.
- 전체 청산 주문의 부분 체결도 모델별 원매수 시각 순서로 나눠 기록한다. 수동 잔여는 그 뒤에 배분하며, 원가를 알 수 없는 수량의 수익은 미확인이다. 이는 앱의 가상 배분 규약이지 증권사가 전략별로 계좌를 나눠 준다는 뜻은 아니다.

## 설치·폴더 구조

### 장부 조회 측정

가짜 장부에서 무관 주문을 1천/5천/1만 건으로 늘리고, 워밍업 5회 뒤 각 50회 측정했다. 다른 테스트도 실행 중이었던 로컬 측정이며 실제 장중 앱 속도 측정은 아니다.

| 무관 주문 수 | 종목 inventory 평균 | 미확정 매수 평균 |
|---|---:|---:|
| 1,000 | 0.735 ms | 0.682 ms |
| 5,000 | 0.729 ms | 0.673 ms |
| 10,000 | 0.722 ms | 0.678 ms |

감사 당시 1만 건의 86.187/85.433 ms에 비해 크게 줄었다. 같은 종목의 장부가 커져도 항상 O(1)이라는 뜻은 아니다. 무관 장부를 읽지 않는 인덱스 SEARCH와 일정한 SQLite 명령 수를 확인했다. 원시 결과는 로컬 `outputs/optimization-audit/rt03-after.json`에 있다.

### 역할별 구현 위치

```text
dockdack/

  persistence/  SQLite·계정 범위·복사 이관·로그 보관

  signals/      외부 모델 프로세스·연결·기존 신호 API
  ui/           일반 화면·패널·로컬 읽기 작업자
  mark1_*.py    봉인된 연구/추론 및 호환 경로 보존
tests/          회귀 검증
scripts/        개발 검증·설치본 smoke
docs/           사용법·기능 목록·감사/개선 기록
models/         별도 검증된 모델 묶음
```

flat Python package + 역할별 하위 패키지를 사용한다. 전체 `src/` 이동은 동결 소스 경로 계약과 기존 실행기를 불필요하게 깨므로 강행하지 않았다. 대신 wheel을 체크아웃 밖에 설치하여 루트의 우연한 import에 기대지 않는지 검사한다. 큰 파일의 존재만으로 기능을 삭제하지 않았다.

## 검증 및 한계

**최종 발견된 회귀 1,925개 전부 통과**했다. 4개 독립 모듈 분할(476/504/441/503개)과 마지막 GUI 추가 회귀를 실행한 뒤, 현재 테스트 ID 1,925개와 성공 로그의 고유 ID 1,925개를 대조하여 누락 0개를 확인했다. 최초 통합 실행에서 드러난 예전 계정 범위/모의 close 인터페이스 fixture 및 UI 문구 기대값도 새 계약에 맞춰 재검증했다. 계정 검증을 느슨하게 바꿔 테스트를 통과시킨 것이 아니다.

일반 `python -m unittest discover`와 명시적 tests 발견 모두 1,925개, 구문 검사·`uv lock --check`·`git diff --check` 통과. 로컬 원시 로그는 `outputs/optimization-audit/final-shard-{1,3,4}.log`, `final-shard-2-rerun.log`, `final-added.log`에 있다. [종료 검증 요약](final-verification.json)도 남겼다. 주문 검증은 가짜 브로커/임시 SQLite를 사용했으며 실제 사용자 DB·키·계좌는 수정/호출하지 않았다.

- 별도 Python 환경에서 wheel과 GUI/prototype 의존성을 설치하고, 저장소 밖에서 두 독립 worker의 국내·미국 실제 저장 모델 로드/추론 4조합 성공.
- 같은 격리 환경에 research/dev 의존성을 추가 설치해 Torch 2.14.0+cpu / NumPy 2.5.3 / CatBoost 1.2.10 / LightGBM 4.6.0 import와 5개 연구 gateway `--help` 성공. 원래 CUDA 학습 환경 재현이나 GPU fitting 결과를 주장하지 않는다.
- 동결 모델·원본 DB의 내용 검증 결과는 [연구 보호 자료 점검](research-fix-verification.json)에 기록한다.
- 감사 시작 인벤토리의 `models/` 파일 60개 전부 SHA-256 불변을 별도로 확인했다. deep 연구 소스 한 파일은 원래 봉인된 LF 바이트로 복원한 것이며 모델 재학습/수식 변경이 아니다.
- 데이터 수집 테스트는 수정주가 혼합 방지, 중단/재시작, 오류 응답, 다른 종목, 동시 수집/원본 변경을 다룬다. 실제 공급자가 전체 이력 snapshot ID를 주지 않는 한 관측되지 않은 임의 과거 정정까지 증명하는 것은 불가능하다.
- 마감 청산은 모의 단위/통합 테스트이며 실제 장중 접수·체결 확인이 아니다. 미체결이나 거절을 숨기거나 미확정 주문을 자동 재전송하지 않는다.
- 모델 성능·백테스트 수익률을 개선했다는 주장은 없다. 기존 연구 미통과·비용 후 손실·장중 경로 한계는 그대로다.
- 설치 검증용 임시 환경 `C:/Users/user/AppData/Local/Temp/dockdack-wheel-f7bcbbb7d8af4948ba8b67c0f7a6d2cf`은 정리 명령이 실행 정책에서 차단되어 남아 있다. 운영 가상환경과 별개이며 삭제 완료로 보고하지 않는다. 검증 wheel/로그는 저장소의 ignored outputs에 보존했다.

## 후속 회귀 수정: VBS 실행기의 장부 경로 전달

위 1,925개 검증 이후 사용자 실행에서 계정 범위 불일치 오류가 발견됐다. 구 실행기가 발견한 공용 장부를 명시적 `--store`로 넘겨 소유 확인 이관 절차를 우회했다. 이전 단위 검증은 이관 함수 자체를 검사했지만 실제 실행기→GUI 시작 연결을 확인하지 않았고, 실행기 테스트도 이전 경로 전달을 정상으로 기대했다.

자동 발견은 `--legacy-store` 원본으로만 전달하도록 수정했다. 계정별 목적지/잠금/소유 확인/원본 보존을 거치며 직접 지정하는 `--store`의 계정 불일치 차단은 유지한다. `DOCKDACK_HOME` 경로도 실행기와 GUI에서 동일하게 적용한다. 실제 사용자 장부는 바인딩만 읽기 전용으로 확인했고 복사·재귀속하지 않았다.

임시 장부를 사용하는 시작 경로 통합 회귀 9개와 경로 회귀 2개를 추가했으며 관련 9개 모듈의 **115개 테스트를 재검증해 통과**했다. 전체 회귀·설치 wheel 검증을 다시 수행한 결과는 아니며, 위 종료 검증 자료는 이 후속 수정 전 시점의 기록이다. 자동주문 시작이나 실제 계좌 호출은 하지 않았다.
