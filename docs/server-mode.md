# GUI 지속 감시 운영 안내

기본은 모의투자이며 실전은 [별도 환경 선택·경고·키 설정](trading-modes.md)이 필요하다. GUI를 켜 두고 감시를 시작하면 시장별 관심종목 선정 → 차트/가격 수집 → 로컬 JSON 전달 →
신호 수신 → 안전 검사 → 모의 주문을 반복한다. **조회 전용 감시와 주문 허용 상태는 별도**다.
Windows 서비스나 HTTP 서버를 설치하지 않으며 앱 종료·절전·인터넷 단절 시 정상적인 지속 동작을 보장하지 않는다.

## 실행 순서

1. 프로젝트에서 `uv sync --extra gui` 후 `DockDack.vbs` 또는 `uv run --extra gui dockdack-gui`를 실행한다.
2. **관심종목 · 자동매매**를 연다. 기존 저장 종목과 과거 일봉은 그대로 나타난다.
3. 초기 목록이 필요하면 **거래대금 TOP100 추가 · 한국 + 미국**을 누른다. 이 수동 버튼은 장외에도 API가 제공하는 최근 순위를 받을 수 있다.
4. **장중 개장·매 정시 TOP100 재선정**을 선택한다. 체크만으로 시작하지 않고 **감시 시작 (조회만)** 후부터 동작한다.
5. 외부 프로그램에 데이터를 보내려면 **외부 신호 연결 → 외부 신호 모드**를 선택한다.
   내장 테스트를 쓸 경우 아래 **모의 테스트 신호기**를 먼저 선택하면 외부 모드가 자동 설정된다.
6. 수량과 시장별 주문당 금액 상한을 입력한다. 기본은 **1주, KRW/USD 모두 0**이며 0인 시장은 주문 차단이다.
7. 조회만 원하면 **감시 시작 (조회만)**을 누른다. 주문까지 원하면 **자동주문 켜기 (ON)**를 누르고 확인한다.
   감시 시작을 따로 누를 필요 없이 전체 조회부터 진행하며, 이미 조회 중이면 완료를 기다려 자동으로 ON이 된다.
   다시 켜기를 누를 필요가 없고 OFF로 예약을 취소할 수 있다. 조회/잔고/사용 중인 신호·선정 오류 시 OFF를 유지한다.
8. **감시·주문 중지**는 다음 전송을 막는다. 이미 전송 중이거나 접수된 주문은 취소하지 않는다.

재시작하면 감시·자동주문은 OFF이며 입력 경로/신호 정책도 다시 확인해야 한다.
프로그램을 실제 실행해 주문하도록 두는 것은 별도 단계다. 이번 구현 검증에서는 API 주문을 보내지 않았다.

## 거래일과 정시 재선정

모의주문의 지원 범위·장전 제외·장외 대기 후 자동 재개는 [모의투자 거래시간 확인](mock-trading-hours.md)을 참고한다.

| 시장 | 일반 거래일 재선정 시각 | 기준 시간대 |
| --- | --- | --- |
| 한국 | 09:00 개장, 10:00~15:00 매 정시 | Asia/Seoul |
| 미국 | 09:30 개장, 10:00~15:00 매 정시 | America/New_York |

미국은 한국 시각 정각이 아니라 **미국 현지 정각** 기준이다. 서머타임에 따라 한국에서 보이는 시간이 달라진다.
개장 직후와 첫 정시의 간격은 미국의 경우 30분이다. 휴장일에는 자동 선정하지 않으며 조기폐장일은 폐장 전 시각까지만 실행한다.

- `exchange_calendars`의 XKRX/XNYS 거래일과 개·폐장 시각을 사용한다. 미국 정규장·2026년 휴장/조기폐장은
  [NYSE 공식 일정](https://www.nyse.com/trade/hours-calendars)과 대조했다.
- 라이브러리에 빠진 국내 2026-06-03 선거일과 2026-07-17 제헌절 휴장을 보완했다.
  근거: [키움 6월 일정](https://invest.kiwoom.com/inv/calendar?date=20260628), [KRX 휴장 공지](https://strn.krx.co.kr/corebbs5/BHPSTRN0401/list).
- **2026-11-19는 국내 특별 개장시간 미확인으로 차단**한다. 라이브러리의 평시 시간을 그대로 사용하지 않는다.
  해당 날짜 전 KRX 공지를 확인하여 `dockdack/market_schedule.py`와 테스트를 갱신해야 한다.
  확인되지 않은 날짜가 일봉 누락 구간에 포함되어도 자동 수집/판단이 막힐 수 있다.
- 모든 미래 임시 휴장이나 특별 개장을 자동 수집하는 것은 아니다. 거래소 공지와 캘린더 업데이트를 정기적으로 점검해야 한다.
- 10:20처럼 정시 사이에 감시를 시작하면 다음 11:00부터 재선정한다. 최초 조회는 바로 실행한다.
- 실행 중 HTTP가 끝난 다음 안전한 지점에서 선정하므로 정시보다 늦을 수 있다. 정시 후 5분까지 허용하며 그보다 늦으면 다음 시각을 기다린다.
- 실패는 같은 시각 안에서 60초 이상 간격으로 최대 3회만 시도한다. 순위/잔고/미체결 조회 실패 시 이전 목록을 유지한다.
- 완료한 시장/시각은 SQLite에 기록해 재시작해도 다시 실행하지 않는다. 중간 종료된 실행은 그 시각에 재실행하지 않고 다음 정시를 기다린다.

### 관심종목 교체 범위

신규 자동등록 종목이 순위 밖으로 나가면 비활성화한다. 과거 차트와 주문 기록은 삭제하지 않는다.
수동 추가/기간 변경한 종목, 보유·미체결 종목, 로컬 미확정 주문, 대기 수동 규칙이 있는 종목은 보존한다.
보유·미체결은 해당 시장 전체 계좌를 조회해 검사한다.

**구버전 DB에는 수동/자동 등록 구분이 없어 기존 관심종목을 모두 보존**한다. 현재 저장된 기존 200종목도 이에 해당한다.
따라서 거래대금 선정 대상은 각각 100개지만 보존 종목까지 합친 전체 감시 목록은 200개보다 많을 수 있다.

일반 기업 보통주 정책을 기존 목록에 적용할 때는 부적격 종목을 비활성화하고 대기 규칙을 정지한다.
보유·미체결·접수 불명 종목은 이력 및 주문 확인을 위해 목록에 남기지만, 보통주로 분류되지 않으면 새 자동주문은 차단한다.
삭제나 임의 청산·미체결 취소는 하지 않는다. 기존 거래대금 순위로 등록된 종목은 관리 대상으로 이관할 수 있으며 그 외 수동 관심종목은 유지한다.
미국 공개 종목분류는 보수적 교차 확인 방식이며 일부 일반주가 누락될 수 있다. 분류 소스 장애가 발생하면 갱신/자동주문을 보류하고 활동 기록을 확인한다.
순위 밖의 기존 종목을 빼려면 감시 중지 후 직접 제외한다. 최대 500개를 넘으면 목록 교체를 실패 처리한다.

## 과거 일봉 저장과 API 사용량

저장소는 `.dockdack/watchlist.sqlite3`의 `history_cache`다. 기존 200종목의 **5,978개 일봉을 이미 로컬 저장**했다.
199종목은 30개, 스카이랩스(386380)는 API가 제공한 8개이며 부족한 값을 만들어 넣지 않는다.
이는 설정한 기간의 최근 N개를 유지하는 지속 캐시다. 모든 과거 일봉을 무한히 누적하는 별도 학습 데이터 창고는 아니다.

- 처음 등록하거나 기간 N을 늘리면 필요한 N거래일을 조회한다.
- 같은 날에는 과거 구간을 재사용하고, 당일 봉만 5분 경과 후 다음 순회에서 갱신한다.
- 재시작해도 DB의 과거 봉을 사용한다. 다음 날에는 새 거래일과 완료 봉 검사용 겹치는 구간만 받는다.
- 며칠 꺼져 있었다면 빠진 거래일을 증분으로 채운다. 장 마감 30초 이후 다음 조회에서 당일 봉을 다시 확인한다.
- 겹치는 완료 봉이 바뀌면 수정주가 변경 가능성이 있으므로 N개 전체를 다시 받는다.
  아주 오래된 봉만 수정된 경우에는 이 검사만으로 발견하지 못할 수 있다.
- 휴장일·마감 후에는 이미 완료된 봉을 반복 요청하지 않는다. **현재가 요청은 매 순회 계속**한다.

여기서 '당일 1개 갱신'은 애플리케이션이 갱신에 사용하는 봉 개수다. 키움 일봉 API에는 이 코드가 사용하는
요청 본문 기준으로 봉 개수 필드가 없어, 응답 한 페이지에 과거 봉이 함께 포함될 수 있다.
따라서 저장 기간 전체의 추가 페이지 조회와 재시작 시 전체 수집을 피하지만 **장중 일봉 API 호출 자체가 0회가 되는 것은 아니다**.
30개가 원래 한 페이지에 들어오던 종목은 장중 5분마다의 HTTP 요청 수가 이전과 같을 수 있다.
캐시 유효 구간·완료된 장외 봉에서는 일봉 요청을 생략한다. 현재가/일봉 API의 실제 요청 간격과 응답 단위는 서로 구분해야 한다.

기존 표시용 차트를 API 호출 없이 저장 형식으로 옮기려면 `uv run python scripts/warm_history_cache.py`를 실행한다.
필요할 때 코드에서 `engine.histories.invalidate(watch_id)` 후 다음 조회로 해당 종목을 전체 재동기화할 수 있다.
DB 전체를 지우는 방식은 주문 중복 방지 기록도 잃으므로 사용하지 않는다.

## 지속 데이터 전달

외부 모드의 기본 경로:

| 파일 | 갱신 시점 |
| --- | --- |
| `.dockdack/exchange/charts_updates/domestic_KRX_005930.json` 등 | 해당 종목 조회 직후 |
| `.dockdack/exchange/charts.json` | 전체 순회 완료 후 |
| `.dockdack/exchange/signals.json` | 외부 신호 코드가 새 판단을 작성 |
| `.dockdack/exchange/random-signals.json` | 내장 테스트 신호기가 종목별 판단을 작성 |

이는 **같은 PC의 로컬 파일 연결**이다. 원격 서버 전송, HTTP/WebSocket 스트리밍, 별도 딥러닝 모델은 포함하지 않는다.
각 파일은 임시 파일에 쓴 후 원자적으로 교체한다. 외부 프로그램은 새로운 `export_id`만 처리하고, 반복 읽을 때 같은 결정을 다시 생성하지 않는다.
개별 파일은 최신 한 건을 덮어쓰는 방식이며 모든 시세 변화를 보관하는 이벤트 큐가 아니다.
제외한 종목의 이전 개별 파일은 자동 삭제하지 않으므로 파일 존재만으로 현재 감시 대상을 판단하면 안 된다.
전체 목록, `quote_fetched_at`, `quote_stale`, `status`를 함께 확인한다. 제외 종목의 주문 신호는 수신 측에서도 차단한다.

기본 30초는 **전체 순회를 마친 뒤 대기시간**이다. 200종목을 모두 30초마다 동시 갱신하는 의미가 아니며,
첫 일봉 수집과 API 제한 때문에 몇 분 걸릴 수 있다. 이후 과거 차트를 재사용해 일봉 호출량을 줄인다.
정시 재선정, 현재 HTTP, 계좌 조회 때문에 전달 지연이 생길 수 있다. 신호 만료 시 주문하지 않는다.
차트의 `history_fetched_at`과 `quote_fetched_at`은 서로 다른 시각이며 API 시세 자체의 지연도 있을 수 있다.

입출력 규격과 예제는 [외부 신호 연결](external-signals.md)을 참고한다.

## 내장 모의 테스트 신호기

**모의 테스트 신호기** 탭의 체크박스를 선택하면 출처 `random-demo`와 전용 입력 파일을 설정한다.
체크를 해제하면 이전 외부 출처/입력 설정을 되돌린다. 설정 자체는 주문을 활성화하지 않는다.

- 새로운 종목 스냅샷마다, 해당 종목을 보유하지 않았으면 **10% 확률**로 설정 수량 매수 신호를 생성한다.
- 이미 보유한 종목은 추가매수하지 않는다. 실제 보유 수량 가중 평균 매입가 대비 현재가가 **+1% 이상이면 익절**,
  **-0.8% 이하면 손절** 신호를 생성한다. 두 경우 모두 매도가능 수량이 충분해야 한다.
- 기본은 매수/매도 모두 **1주**다. 여러 주를 보유해도 한 신호로 전량 청산하는 방식은 아니다.
- 다른 경우는 HOLD다. 장외, 금액 한도 0, 미확정/미체결 주문 상태에서는 새 주문 신호를 만들지 않는다.
- 같은 `export_id`/종목은 난수를 다시 뽑지 않고 DB에 저장된 결정을 재사용한다. 새 데이터의 새 판단은 새 신호가 된다.
- 신호용 잔고는 최대 30초 재사용하지만, 주문 직전에는 잔고·미체결·현재가를 다시 조회한다.
  익절은 최신 평균 매입가 대비 +1%와 신호 생성 시 최소 매도가를 모두 만족해야 한다.
  손절은 최신 평균 매입가 대비 -0.8% 조건을 다시 만족해야 하며 가격이 회복되었으면 전송하지 않는다.
  손절 신호에 익절의 최소 매도가를 붙이지 않으며 로그에 익절/손절을 구분한다.
- 국내는 **시장가**로 전송한다. 미국 모의 API는 이전 실제 응답 `RC4065`에서 시장가를 거부했다.
  기본은 미국 주문 차단이며 사용자가 **미국 현재가 재조회 → 지정가**를 선택한 경우에만 이 방식으로 주문한다.

이것은 연결 확인용 확률 신호기이지 수익성이 검증된 전략이 아니다. 10%는 새 스냅샷 판단마다의 독립 확률이며,
관심종목의 정확히 10%만 매수한다는 뜻은 아니다. 장시간 감시하면 많은 종목이 매수 신호를 받을 수 있다.
+1% / -0.8%는 **현재가 기준 신호 조건**이지 실제 체결가격·순수익 또는 손실 한도 보장이 아니다.
시장가 슬리피지·수수료·세금, 순회/API 대기 지연, 지정가 미체결로 결과가 달라질 수 있다. 특히 매도도 기본 1주여서 전량 청산이 아니다.
금액 한도는 주문당이며 하루 누적 주문 수, 총 포트폴리오 노출, 계좌 누적 손실 한도는 별도로 구현되지 않았다.
미체결·불명확한 접수 결과는 재시도하지 않는다. [주문 기록과 차단 해제](autotrading.md)를 따라 확인해야 한다.

## 체결가 보완과 손익 확인

감시 중에는 가격이 없는 로컬 자동주문 기록을 검사하고 필요한 시장·거래일 체결 내역을 조회한다.
검사는 최소 60초, 같은 묶음의 자동 재시도는 300초 이상이며 수동 **체결가 다시 확인**도 최소 60초를 지킨다.
한 번에 최대 4개 시장·조회일 묶음만 조회하고 다른 API 요청과 같은 작업 스레드·호출 속도 제어를 사용한다.
실패도 대기시간에 포함하며 저장된 확인 시각으로 재시작 직후의 연속 조회를 방지한다.

이 조회는 주문 전송·취소나 접수 상태 변경을 하지 않는다. 조회 범위와 주문 식별 정보가 일치하고
단일 1주 체결가가 확인된 경우만 가격을 보완한다. 여러 체결의 평균가 의미가 불명확하거나 기록이 없으면 미확인을 유지한다.
미국 과거 조회는 API 조회일의 시간대 근거가 미확인이므로 가격 보완을 보류한다. 기존 당일 주문 체결 확인과 별개다.
기존에 확인한 체결 수량보다 적은 응답으로 되돌리지 않으며 같은 수량의 가격 누락 응답으로 기존 가격을 지우지 않는다.

**실제 주문·체결**의 실현손익은 전체 로컬 자동주문 장부의 주문순서 FIFO 기준이며 수수료·세금 제외다.
매수 기록·체결가가 없으면 원가/손익을 0으로 만들지 않는다. 수동·다른 앱 주문 및 기존 계좌 보유분을 전부 반영한 계좌 손익이 아니다.
화면의 500건 표시 제한, 조회일·가격 근거와 미확인 처리의 상세는 [체결가 보완과 실현손익](gui.md#체결가-보완과-실현손익)을 참고한다.

## 보관 및 운영 제약

- API 키는 `.env`, 데이터와 주문 이력은 `.dockdack/`에 두며 모두 Git에서 제외한다.
- 과거 봉·결정·신호·주문 기록은 자동 삭제하지 않아 장기 운영 시 DB가 커질 수 있다. 디스크 여유와 백업을 관리한다.
- 하나의 모의 계좌에 하나의 실행 인스턴스를 권장한다. DB를 복사해 동시 주문하거나 계좌 키만 바꿔 같은 DB를 쓰지 않는다.
- 실제 주문 송신 없이 가짜 브로커/HTTP와 임시 DB로 주문 경로를 검증했다. 실제 미국 정상 접수·체결은 아직 미검증이다.
